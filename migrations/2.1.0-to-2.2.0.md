# Migrate protocol 2.1.0 to 2.2.0

## Preconditions

- The target has a valid `.agent/protocol.lock.yaml`.
- The lock records protocol version `2.1.0` and entrypoint digest
  `sha256:de6c730cf2b06fda8deca373cb7b522f16b58467e43dc52824000f87f70913fa`.
- Protocol-managed paths can be reconciled without overwriting project-owned content.
- No same-version digest fork or unresolved local divergence exists.

## Operations

1. Add the `evidence-to-scope-cross-questioning` rule to `AGENTS.md`: safely archive a complete
   external feature intake as unverified, audit one coherent feature against source/tests and
   existing planning records, classify coverage, and resolve only material human choices before
   accepting scope. Add the `skipped-client-questions-block-milestones` rule: every explicitly
   skipped material question with accepted milestone ownership becomes a blocked client-question
   task, blocks that milestone, and remains in the grouped client handoff until reconciled.
2. Reconcile `.agent/client-log.md` guidance so multi-feature intake distinguishes unreviewed items,
   coverage findings, open client-question task links, accepted answers, and linked absorbed outcomes
   without replacing existing evidence or exposing secrets, raw identifiers, or full PII.
3. Reconcile `.agent/todo.md` guidance so fully supported behavior creates no task, partial gaps
   refine their existing owner, and new milestones are created only for distinct accepted outcomes.
   Add `State: Active` or `State: Blocked` to every open milestone. Preserve every project-specific
   milestone, task, priority, ID, task state, source anchor, dependency, and acceptance condition.
4. During a cross-questioning pass, when the human explicitly skips a material question and accepted
   evidence identifies its owning milestone, allocate a unique task ID for a `Blocked`
   client-question task containing exact client-ready wording, source linkage, and acceptance that
   requires answer archival plus milestone-fact reconciliation. Mark the owning milestone `Blocked`.
   Do not synthesize questions from historical evidence during upgrade, invent a milestone when no
   accepted outcome exists, or add feature work merely because this migration introduces the rule.
5. After verification, update `.agent/protocol.lock.yaml` to version `2.2.0`, set
   `last_applied: 2.2.0`, append `2.1.0-to-2.2.0` once, and add
   `evidence-to-scope-cross-questioning` and `skipped-client-questions-block-milestones` once each to
   `managed.rules`.

## Verification

- A multi-feature fixture archives the complete safe intake while promoting only the one feature
  whose material questions were answered; unanswered features remain explicitly unverified.
- A fully supported fixture produces a coverage finding and no new task or milestone.
- A partial-coverage fixture updates the existing owning task without duplicating it, while a
  distinct accepted outcome receives one new milestone with explicit priority and closure evidence.
- A missing or unanswered material choice does not become accepted scope, and no product code,
  deployment, message, or other external effect is inferred.
- An explicitly skipped material question with accepted milestone ownership creates one blocked,
  client-ready task per independently answerable question, marks that milestone blocked, and appears
  in the final unsent handoff grouped by milestone/task ID.
- A returned answer is appended as accepted client evidence, added to the corresponding milestone's
  facts, and reconciled into affected scope records before the client-question task is removed. The
  milestone becomes active only after no skipped question or other blocker remains.
- Existing project prose, priorities, milestones, tasks, decisions, evidence, and unrelated paths
  remain unchanged.
- Internal links, immutable IDs, source anchors, target verification, and declared digests pass.
- A repeated 2.2.0 reconciliation produces zero diff.

## Abort behavior

Stop without advancing the lock if a precondition, ownership check, evidence reconciliation, or
verification step fails. Revert only changes attributable to this migration; never use destructive
Git operations.
